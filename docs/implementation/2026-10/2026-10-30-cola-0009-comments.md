# COLA-0009: `//` comments, carried through the model and `fmt`

## Premise

`docs/design/2026-10-30-value-language.md` decides comments: `//` to
the end of the line inside cola blocks, layout to the grammar, never a
value; attached to the model as leading or trailing comments so that
`colap fmt` keeps them. COLA-0007 left them out because they are the
one form that does not fall out of the grammar: the parser discards
layout, so the builder has to find them in the block text and attach
them by position. This ticket closes the value-language task.

## Decisions taken in planning

- **Attachment** follows the design record, made precise. A comment on
  the same line as the end of a field, an entity header or an
  entity's `;` is the **trailing** comment of the item that ends last
  on that line before it. Any other comment is a **leading** comment
  of the next item (field or entity) among the direct items of the
  innermost entity that contains it; when no item follows, it is a
  leading comment of that entity's close (`;`); at the top of a block
  with no entity after it, it belongs to the end of the block. A
  comment on a line inside a multi-line list, which is neither on the
  list's last line nor before the field, is a leading comment of the
  field. A `//` inside a string is text, not a comment.
- **Model**: a `Comments { leading: Vec<String>, trailing:
  Option<String> }` on every field (`ConfigField::comments`) and two on
  every entity: `comments` for its header and `closing` for its `;`.
  The root entity's `closing.leading` holds end-of-block comments. The
  text is kept as written after `//`, trailing whitespace trimmed.
- **Builder**: the comment scan reuses the highlighter's line lexer,
  which already knows strings and block strings across lines, so the
  parser, the editor and the formatter agree on what a comment is.
  `ModelBuilder::add_block` therefore takes the block body as well as
  the AST (a breaking change to a 0.3 signature, recorded in the
  changelog).
- **Canonical layout**: leading comments on their own lines at the
  item's indentation; a trailing comment after the item's comma, the
  header's colon or the `;`, one space away. An entity is written on
  one line only when its header has no trailing comment, none of its
  fields has a comment and nothing stands before its `;`; a comment
  after the `;` keeps the one-line form (`a: x: 1; // note`). Comments
  inside a list are not written back inside it (see attachment).
- **Not in this ticket**: a warning for two fields with no comma
  between them; it is a separate decision.

## Action items

1. **Grammar**: `Layout` becomes whitespace or a `Comment` terminal
   `//` to end of line; the generated parser is regenerated.
2. **Highlighter**: `TokenKind::Comment`; the lexer function is shared
   with the builder.
3. **Model**: `Comments`, the three slots above, `Default` and
   constructors kept source-compatible where possible.
4. **Builder**: `add_block(&ast, body, line_offset)` attaches comments
   in one source-order walk; `format.rs` and `lib.rs` pass the body.
5. **Canonical layout**: the rules above; `to_cola` ends with the
   block-end comments.
6. **Spec**: section 3 gains the comment rule (and loses "there are no
   comments"), section 5 the attachment, section 7 the layout, section
   9 the item; README table row and the "one open decision" sentence;
   CHANGELOG `Unreleased`.
7. **Tests**: `tests/conformance/valid/comments.md` with every
   placement; `tests/data/fmt/comments.md` with its `.expected.md`;
   `tests/comments.rs` pins attachment, round trip and idempotence;
   the task file is set done.
